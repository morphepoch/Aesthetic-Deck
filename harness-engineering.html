WHY NOW

单靠 Prompt 和 Context，
已经扛不住了。

01
Prompt 不够
复杂任务一条 prompt 解决不了。逻辑散落各处，难以版本化，出错不知从哪改。
02
长 Context 也不够
Context 越长延迟越高、成本越贵。存在 lost-in-the-middle 问题，中段内容被模型遗忘。
03
Agent 持续工作暴露新问题
环境、状态、知识、反馈回路——旧范式完全没有原语覆盖。一旦 agent 持续工作，系统就失控。
从"写代码解决问题" → "设计环境、工具、反馈回路让 agent 解决问题"
工程师角色转变的本质：从代码编写者到 agent 驾驭者
工程范式转变的起点不是模型，而是控制面的缺失

Harness 组成  ·  Five Components
04 / 10
Harness = 不只是 Prompt，而是一套可控系统

Harness 的五个组成

按 → 键逐步展开  ·  每一层缺一不可

01 · Environment
环境
文件系统、代码仓库、浏览器、终端。没有真实环境，agent 只是会聊天的模型。
02 · Tools
工具
代码执行、API 调用、文件读写、数据库查询、浏览器操作。工具定义了 agent 的行动边界。
03 · Knowledge
知识
wiki、设计文档、规范、代码注释。不是训练进权重的，而是运行时可查询的。
04 · Feedback
反馈回路
测试通过/失败、lint 结果、用户评分、人工介入。没有反馈，agent 就是黑箱。
05 · Constraints
约束
操作权限、安全边界、不可逆操作需人工审批。这是可控性的工程保障。
可控性 Controllability  ·  可观测性 Observability  ·  可恢复性 Recoverability
Harness 的三个核心工程原则
五个组成顺序即依赖关系：环境先于工具，工具先于知识

Runtime Substrate  ·  Thread / Turn / Item
05 / 10
从多轮聊天到结构化 Runtime
Thread
完整任务的生命周期容器。可跨多个 Turn 持续运行，拥有独立状态和历史。
Turn
一次人-Agent 或 Agent-Tool 的交互单元。每个 Turn 包含若干 Item。
Item
Turn 内部的结构化事件：user_message / tool_call / tool_result
App Server
管理多 Thread 状态，处理状态压缩（state compaction），暴露工具和上下文给 Agent。
结构化带来：状态压缩  ·  检查点恢复  ·  并行多 Thread
Thread # 完整任务容器 ├── Turn 1 # 第一轮交互 │ ├── Item: user_message │ │ "帮我分析这个仓库" │ ├── Item: tool_call │ │ read_file("src/main.py") │ └── Item: tool_result │ {content: "class Agent..."} └── Turn 2 # 继续执行 ├── Item: assistant_message │ "发现 3 个潜在问题..." ├── Item: tool_call │ run_tests() └── Item: tool_result {passed: 42, failed: 1}
vs 传统多轮对话：所有历史拼成一个大 string 塞进 context
Thread / Turn / Item 是 Harness Runtime 的骨架原语，不是聊天记录

资源分层  ·  Knowledge vs State
07 / 10
五类资源，各归其位

知识层 vs 状态层

知识层  ·  相对静态，可共享
Resource / Wiki
知识库
设计文档、API 规范、代码注释、团队 wiki
存储：向量数据库（pgvector / Chroma / Milvus）
接入：RAG 检索，按需注入当前 turn context
图书馆 · 人人可查，不属于任何一个 agent
Skill
技能库
可复用的工具函数、prompt 模板、操作步骤
存储：代码仓库 / 工具注册表
接入：工具调用（function calling / MCP）
工具箱 · 拿来即用
状态层  ·  动态，用户 / 会话绑定
Profile
用户画像
用户偏好、角色、历史行为摘要
存储：PostgreSQL users 表 + 定期更新
接入：会话开始时注入 system prompt
员工档案
Memory
长期记忆
跨 session 的事实、偏好、重要决策记录
存储：PostgreSQL + 向量索引（支持语义检索）
接入：新会话开始时检索相关记忆注入
日记本 · 按需翻阅
Working Memory
工作记忆
当前 thread 内的临时状态、任务进度、中间结果
存储：thread 的 item 流 + 内存（不持久化）
接入：当前 context window 直接可见
桌面便利贴 · 会话结束即清
⚠ 最常见错误 把所有东西混进一个大 context  ·  正确做法：按类型分层存储，按需检索注入
五类资源 · 两层架构 · 统一的工程控制面

Production vs Evaluation  ·  Harness
08 / 10
两种 Harness，一个共同内核

搭系统 vs 量系统

Production Harness
生产环境
目标
让 Agent 在真实环境中可靠工作
组成
环境 + 工具 + 知识 + 反馈 + 约束
关注
延迟 · 成本 · 可控性 · 可恢复性
输入
用户真实请求
反馈
用户行为 / 满意度（实时）
典型
OpenAI Codex · Claude Code · 内部知识助手
Evaluation Harness
评测体系
目标
量化 Agent 的能力边界和质量
组成
任务集 + 证据 + 评分口径 + 代价矩阵
关注
准确率 · 召回率 · 任务完成率 · 幻觉率
输入
标准化任务集（benchmark）
反馈
Ground truth 对比（版本发布时）
典型
ConvoMem · SWE-bench · 内部 benchmark
共同内核：结构化环境  ·  明确任务定义  ·  可观测执行路径  ·  反馈回路
评测 Harness 是生产 Harness 的质量镜像——往 infra / benchmark 方向走的工程师需要同时理解两者
两种 Harness 共享设计语言，只是服务目标不同

MVP 路径  ·  Python / TS + Postgres / Docker
09 / 10
后端工程师的最小落地路径

四步 MVP 路径

按 → 键逐步展开  ·  每一步都可独立交付

Step 01  ·  能回答问题
RAG + 单工具调用
单 thread，接 pgvector 知识库，一个工具调用。能回答问题，能查文档。

FastAPI + LangGraph + psycopg2 + pgvector
Step 02  ·  记得用户是谁
Profile + Memory 持久化
users 表存 Profile，memories 表 + pgvector 存长期记忆。跨 session 不失忆。

PostgreSQL users + memories 表
Step 03  ·  支持长任务
Working Memory + 状态压缩
thread item 流作为 working memory，App Server 做状态压缩。不再被 context 窗口限制。

Redis 临时状态 + PostgreSQL 持久化
Step 04  ·  量化能力边界
评测 Harness 接入
构建 benchmark 任务集，接入评分口径。知道 agent 在哪弱，迭代有方向。

Ragas / 自建评测管道
Python · FastAPI · LangGraph
TypeScript · Vercel AI SDK · Prisma
PostgreSQL + pgvector
Redis · Docker Compose
OpenAI API · Claude API
pgvector 一个库搞定向量检索 + 关系数据，不需要引入额外向量数据库

The Takeaway
Prompt 关注 怎么说  · Context 关注 给什么背景  · Harness 关注怎样搭一个 可控、可观测、可恢复 的 Agent Runtime
三条行动
→ 用 pgvector 搭知识库，替换临时 RAG 实验
→ 用 thread / turn / item 结构化你的 agent 状态
→ 分清 working memory / memory / wiki 的边界
五个最常见误解
01 "Harness 就是换名字的 RAG" → RAG 只是知识层的检索方式
02 "Context 越长越好" → lost-in-middle 是真实且昂贵的问题
03 "Memory = 历史对话存数据库" → Working Memory ≠ Memory
04 "评测 harness 和生产无关" → 两者共享结构化内核
05 "配好 schema 就完了" → 工具还需权限 · 重试 · 结果结构化
