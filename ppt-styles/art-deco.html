核心差异

Prompt单次交互 · 指令导向
Context多轮对话 · 信息导向
Harness有状态系统 · 行为导向

第一次是 Prompt Engineering，核心是单次交互，用更好的指令引导模型。

第二次是 Context Engineering，核心是信息管理，把外部知识、历史对话塞到上下文窗口。

但问题是——两者本质上都是无状态的。你无法可靠地控制 Agent 的行为。

这就引出了 Harness Engineering：把 Agent 看作有状态的系统，在运行时控制它的行为。

设计原则

环境 — Agent 所处的上下文，包括时间、位置、权限
工具 — Agent 可以调用的 API 和能力
知识 — Agent 可以访问的知识库和记忆
反馈 — 对 Agent 行为的评价和修正信号
约束 — 对 Agent 行为的硬性限制和安全边界

Harness 有五大核心组成，一个都不能少。

Environment 是 Agent 所处的环境，Tools 是它能调用的工具，Knowledge 是它能访问的知识。

Feedback 是反馈回路，Constraints 是硬性约束——这两个是保证 Agent 安全可控的关键。

Runtime Architecture

Runtime Substrate 四层架构

App Server

应用服务层 — 对外暴露 API，管理会话

Thread

会话层 — 管理对话线程，维护全局状态

Turn

回合层 — 处理单轮交互，协调工具调用

Item

执行层 — 原子操作，如消息、工具调用、状态变更

Runtime Substrate 分为四层架构。

最上层是 App Server，负责对外 API 和会话管理。

Thread 层管理整个对话线程，维护全局状态。Turn 层处理单轮交互，协调工具调用。

最底层是 Item 层，处理原子操作，比如单条消息、单个工具调用、状态变更等。

Knowledge & State

知识层与状态层的位置

知识层

Resource — 外部资源，API、数据库
Wiki — 静态知识，文档、FAQ
Skill — 技能库，可复用的能力模块

状态层

Profile — 用户画像，长期记忆
Memory — 对话记忆，短期上下文
Working Memory — 工作记忆，当前任务状态

知识层和状态层要分开设计。

知识层是相对静态的，包括 Resource 外部资源、Wiki 文档、Skill 技能库。

状态层是动态的，包括 Profile 用户画像、Memory 对话记忆、Working Memory 工作记忆。

两者配合，Agent 才能既有长期知识，又有短期状态。

Dual Roles

生产 Harness 与评测 Harness

生产 Harness

在真实环境中运行，处理用户请求

评测 Harness

在受控环境中测试，收集反馈数据

关系

两者共享相同的五大核心组件，但配置和约束不同。评测产生的数据可以改进生产。

生产 Harness 和评测 Harness 是相辅相成的。

生产 Harness 在真实环境中运行，处理用户请求；评测 Harness 在受控环境中测试，收集反馈数据。

两者共享相同的五大核心组件，但配置和约束不同。评测产生的数据可以用来改进生产系统。

容器化运行环境

落地 Harness 并不需要复杂的技术栈。

用 Python 或 TypeScript 写业务逻辑和 Agent 控制。

用 Postgres 做状态持久化，保存 Thread、Memory、Profile。

用 Docker 做部署和隔离，简单可靠。

Pitfalls

最容易误解的 5 个点

1. Harness ≠ 提示词库

提示词只是知识层的一小部分，更重要的是运行时控制

2. 状态 ≠ 对话历史

对话历史只是 Memory，还有 Profile 和 Working Memory

3. 工具 ≠ 插件

工具调用要有安全约束和审计，不是随便什么都能调

4. 反馈 ≠ RLHF

反馈可以是简单的规则和评分，不一定非要强化学习

5. 约束 ≠ 限制能力

约束是为了安全可靠，也是为了 Agent 做得更好更聚焦

这 5 个误解我见过很多次。

1. Harness 不是提示词库，提示词只是知识层的一小部分，更重要的是运行时控制。

2. 状态也不等于对话历史，对话历史只是 Memory，还有 Profile 和 Working Memory。

3. 工具不是插件，工具调用要有安全约束和审计。

4. 反馈不是非要 RLHF，简单的规则和评分也有用。

5. 约束不是限制能力，而是让 Agent 更安全可靠、更聚焦。
