Harness Engineering

从 Prompt / Context 到 Agent Runtime 的工程转向

周启明 · 组内技术分享

为什么后端工程师开始关心 Harness

单靠 Prompt 扛不住

  • 复杂任务需要多轮思考
  • 知识截止日期问题无法解决
  • 没有外部交互能力
  • 状态无法持久化

单靠大 Context 也不够

  • 大海捞针问题
  • 计算成本过高
  • 中间信息易被忽略
  • 没有结构化的知识管理

核心洞察：Agent 一旦要持续工作，就会遇到环境、状态、知识、反馈回路的问题——这些不是 prompt 技巧能解决的，而是系统问题。

这一页想讲清楚：为什么我们不能继续只玩 prompt 和 context。当 Agent 需要持续工作、执行操作、记忆历史时，原来的范式就不够用了。这正好是我们后端工程师擅长的领域——系统设计。

这一页讲三个阶段的区别：Prompt Engineering 关注怎么说，Context Engineering 关注给什么背景，Harness Engineering 关注怎么搭系统。这是一个从简单指令到复杂系统的演化过程。

Harness 的五个组成部分

1. 环境 Environment

Agent 运行的环境，包括文件系统、API、工具等

2. 工具 Tools

Agent 可以调用的工具集，比如函数、API、数据库

3. 知识 Knowledge

知识库、文档、记忆系统，给 Agent 提供信息

4. 反馈回路 Feedback

评估、修正、持续优化的机制

5. 约束 Constraints

权限控制、安全边界、成本限制

Harness 不是简单的 prompt 集合，而是五个组成部分的系统：环境、工具、知识、反馈回路和约束。这是一个完整的工程框架，而不是简单的文本提示技巧。

Runtime Substrate 与内存系统

Runtime 概念

  • Thread - 会话线程，管理整个对话
  • Turn - 每一轮交互，Agent 的一次思考行动循环
  • Item - 每一个具体项目，比如消息、工具调用、思考过程
  • App Server - 服务端，提供状态管理、持久化、API

内存分层

  • Resource / Wiki - 长期知识，稳定不变
  • Profile / Memory - 用户或 Agent 记忆
  • Skill - 技能和模式库
  • Working Memory - 当前工作记忆

为什么需要分层

  • 成本 - 不同存储成本不同
  • 性能 - 速度和容量的权衡
  • 安全 - 不同级别的访问控制
  • 架构 - 清晰的关注点分离
这一页讲 Runtime 的概念：Thread、Turn、Item、App Server，以及内存分层：Resource/Wiki、Profile/Memory、Skill、Working Memory。

生产 Harness 和评测 Harness 的关系

生产 Harness

  • 面向真实用户
  • 稳定性和安全性优先
  • 性能优化很重要
  • 监控和可观测性

评测 Harness

  • 面向测试和评估
  • 可复现和标准化
  • 收集性能数据
  • 基准测试和对比

关键点：生产 Harness 和评测 Harness 共享核心概念，但侧重不同。评测 Harness 帮助我们改进生产 Harness。

这一页讲生产 Harness 和评测 Harness 的关系。两者共享核心概念，但生产 Harness 关注稳定性，评测 Harness 关注评估。

Python / TypeScript + Postgres / Docker 下的最小落地

技术栈选择

  • Python 或 TypeScript - 主业务逻辑
  • Postgres - 状态持久化
  • Docker - 环境隔离
  • Redis - 缓存和会话

核心组件

  • API Server - 接口层
  • Agent Runtime - 执行层
  • Database - 持久层
  • Vector Store - 知识库

最小化原则：从最简单的可用版本开始，逐步增加复杂度。不要一开始就试图构建完美的系统。

这一页讲最小落地的技术栈：Python/TypeScript + Postgres + Docker。强调从最简单的可用版本开始。

最容易误解的 5 个点

1. Harness ≠ 更复杂的 prompt

不是简单地把 prompt 写得更长更复杂，而是构建完整系统。

2. Context ≠ 越长得越好

长上下文不是万能药，需要结构化的知识管理。

3. Agent ≠ 完全自主

不需要让 Agent 完全自主，关键是可控和可靠。

4. 工具 ≠ 越多越好

工具数量不重要，重要的是工具设计合理且可靠。

5. Harness Engineering ≠ 抛弃传统工程

而是在传统软件工程基础上，增加 Agent 相关的设计。

这一页讲最容易误解的 5 个点：Harness 不是更复杂的 prompt，Context 不是越长越好，Agent 不是要完全自主，工具不是越多越好，Harness Engineering 不是抛弃传统工程。

总结

从 Prompt → Context → Harness

核心要点

  • Harness 是系统工程，不是 prompt 技巧
  • 关注可控性、可观测性、可恢复性
  • 从最小可用版本开始迭代
  • 后端工程师的系统设计能力很重要
