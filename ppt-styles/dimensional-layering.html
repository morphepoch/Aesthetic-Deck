// 01 · 为什么现在

为什么后端工程师开始关心 Harness？

🚀

OpenAI 的实验：5 个月，百万行代码

2026 年 2 月，OpenAI 团队分享了他们用 Codex Agent 构建生产系统的真实经历：工程师不再直接写代码，而是变成了智能体驾驭者。

🧩

Prompt + Context 不够用了

当我们需要 Agent 自主完成多步任务、处理失败、跨会话持久化时，单纯的提示词和上下文管理已经不够支撑一个生产级系统。

先从一个问题开始：为什么是现在？为什么 suddenly 大家都在聊 Harness？

因为 2026 年 2 月 OpenAI 发了那篇博客，不是在讲理论，是在讲他们 真实地用 Agent 交付了一个百万行代码的生产系统。这件事给业界的冲击很大。

更重要的是，很多人（包括我之前）以为：做 AI 应用不就是写好 Prompt，加上 RAG 提供 Context 吗？但真要做成一个稳定、可观测、可恢复的系统时，你会发现 Prompt 和 Context 只是冰山一角。

那一角之下是什么？就是今天要讲的 Harness。

// 02 · 三种范式

Prompt / Context / Harness：三次范式转移

2020-2022

Prompt Engineering

指令-响应

  • 告诉 AI 每一步做什么
  • Zero-shot, Few-shot, CoT
  • 核心：把话说明白

2022-2024

Context Engineering

上下文-理解

  • 给 AI 提供足够背景信息
  • RAG, 长上下文, 记忆
  • 核心：把料给够

2024-

Harness Engineering

目标-自主

  • 告诉 AI 目标，让它自己想办法
  • 环境、工具、反馈、约束
  • 核心：把系统搭对

这一页我整理了 AI 工程化的三次范式转移。大家可以对照一下自己现在在哪一步。

2020 到 2022 年是 Prompt Engineering。那时候我们在研究怎么把话说清楚：Zero-shot, Few-shot, Chain-of-Thought。核心是把指令写明白。

2022 到 2024 年是 Context Engineering。我们发现光指令不够，AI 需要背景信息，所以搞 RAG，搞长上下文，搞记忆系统。核心是把料给够。

但到了 2024 年之后，我们进入了 Harness Engineering。为什么？因为当我们真要让 Agent 自主去完成一个复杂目标时，你会发现：Prompt 和 Context 只是输入，真正决定成败的是整个运行环境。

下一页我们就看 Harness 到底包含什么。

// 03 · Harness 组成

Harness 的四大支柱

🌍 环境 (Environment)

Agent 工作的真实环境：文件系统、Shell、数据库、网络访问。没有环境，Agent 只是在空想。

🔧 工具 (Tools)

Agent 能调用的能力：API、函数、SDK。接口如何设计、权限如何控制，直接决定 Agent 能做什么。

📚 知识 (Knowledge)

领域特定信息：文档库、Wiki、代码库。RAG 只是其中一种形态，更重要的是知识如何组织和检索。

⚡ 反馈 + 约束 (Feedback + Constraints)

成功/失败的信号、安全护栏、边界条件。这是让 Agent 从随机漫步变成可靠执行的关键。

核心公式

Harness = 环境 + 工具 + 知识 + 反馈 + 约束

好，现在进入核心：Harness 到底是什么？它包含四大支柱，我一个一个说。

第一个是 Environment（环境）。这是 OpenAI 反复强调的一点：Agent 需要在真实环境里工作，不是在空想。文件系统、Shell、数据库——这些都是环境的一部分。

第二个是 Tools（工具）。Agent 能调用哪些 API？接口怎么设计？权限怎么控制？这直接决定了 Agent 的能力边界。

第三个是 Knowledge（知识）。RAG 只是知识的一种形态，更重要的是知识如何组织、索引和检索。

第四个是 Feedback + Constraints（反馈和约束）。这是最容易被忽略但其实最重要的：Agent 做对了有什么信号？做错了有什么护栏？边界在哪？

这四个加起来，就是 Harness。再看下一页更具体的 Runtime。

// 04 · Runtime Substrate

Runtime Substrate：从 Thread 到 App Server

T

Thread（线程）

一次完整的对话，包含多个 Turn

U

Turn（回合）

一次用户输入 + Agent 响应，包含多个 Item

I

Item（步骤）

一次推理、一次工具调用、一条消息

A

App Server（应用服务器）

管理状态压缩、持久化、跨会话恢复

光有概念不够，还得看 Runtime。OpenAI 在另一篇博客里把它叫 Runtime Substrate，我觉得翻译得很好——运行时基底。

从上往下看：最上层是 Thread（线程），也就是一次完整的对话。一个 Thread 包含多个 Turn。

中间是 Turn（回合），也就是一次用户输入加上 Agent 的响应。一个 Turn 又包含多个 Item。

底层是 Item（步骤），这是最小单位：一次推理、一次工具调用、一条消息。

最下面托着这一切的是 App Server，它负责状态压缩、持久化、跨会话恢复。这部分是我们后端工程师最熟悉的领域。

// 05 · 知识与状态层

Resource / Wiki / Skill / Memory 在 Harness 里的位置

📄 Resource / Wiki（静态知识）

不会随时间变化的文档、代码库、知识库。这是 Agent 的背景书架。

🔧 Skill（能力模块）

可复用的工具组合、API 封装、流程模板。让 Agent 学会固定的做事方式。

👤 Profile / Long-term Memory（长期记忆）

用户偏好、历史对话摘要、重要决策记录。跨会话持久化的个人化信息。

🧠 Working Memory（工作记忆）

当前对话的上下文、正在执行的任务状态、中间结果。随对话动态更新。

这一页专门回答大家关心的问题：Resource、Wiki、Skill、Memory 这些概念在 Harness 框架里分别放在什么位置？

Resource / Wiki 是静态知识层——不会随时间变化的文档、代码库，相当于 Agent 的背景书架。

Skill 是能力模块层——可复用的工具组合、API 封装，让 Agent 学会固定的做事方式。

Profile / Long-term Memory 是长期记忆层——用户偏好、历史摘要，跨会话持久化。

Working Memory 是工作记忆层——当前对话的上下文、任务状态，动态更新。

好，下一页讲生产和评测的关系，然后是最小落地。

// 06 · 生产 vs 评测

生产 Harness 和评测 Harness 的关系

🏭 生产 Harness

  • 面向真实用户场景
  • 注重稳定性、安全性
  • 有完善的错误恢复机制
  • 可观测、可监控

🧪 评测 Harness

  • 面向测试场景，可复现
  • 注重评测指标、基准测试
  • 隔离环境，方便对比
  • 自动化、可批量执行

核心共识

两者共享同一套抽象：都需要结构化环境、证据收集、执行路径和反馈回路。

很多人会问：那我们做的评测 Harness 和生产 Harness 是什么关系？

生产 Harness 面向真实用户——要稳定、要安全、有完善的错误恢复和监控。

评测 Harness 面向测试场景——要可复现、有明确的评测指标、方便批量对比。

但它们共享同一套核心抽象：都需要把环境、证据收集、执行路径和反馈回路给结构化出来。这其实是好事——意味着我们在评测里积累的经验，可以直接用到生产里。

// 07 · 最小落地

Python / TypeScript + Postgres / Docker 下的最小落地

🧱 技术选型

后端用你熟悉的 Python 或 TypeScript，状态存在 Postgres，环境用 Docker 容器隔离。

🏗️ 核心组件

  • Thread/Turn/Item 表：存对话历史和执行轨迹
  • 工具注册中心：管理 Agent 能调用的 API
  • 状态持久化层：处理快照和恢复

🎯 起步建议

先从一个明确的任务场景开始（比如代码审查、数据迁移），不要一开始就做大而全。

好，最后给大家一个后端视角的最小落地建议，毕竟我们都是做工程的。

技术选型别纠结——用你最熟悉的 Python 或 TypeScript，状态存在 Postgres，环境用 Docker 容器隔离，这些都是我们已经玩得很溜的东西。

核心组件也就三块：存对话历史和执行轨迹的表、工具注册中心、状态持久化层。

起步建议很重要——先从一个明确的小任务场景开始，比如代码审查助手、数据迁移流程自动化，不要一开始就想做大而全的平台。小步快跑，快速迭代。

// 08 · 常见误解

最容易误解的 5 个点

1. Harness 不是换名字的 Prompt Engineering — 它是更完整的系统框架
2. Agent 不是越聪明越好 — 稳定、可观测、可恢复比炫技更重要
3. Context 不是越长越好 — 关键在信息组织和检索质量
4. 不要等完美了才上线 — 从简单场景开始，在迭代中完善
5. 工程师的角色没变 — 还是设计系统、管理复杂度、保证质量
