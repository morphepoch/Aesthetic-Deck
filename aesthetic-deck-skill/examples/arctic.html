// 为什么现在

为什么后端工程师突然开始关心 Harness

因为我们遇到了两个用「Prompt + 大 Context」解决不了的问题。

1. Agent 一旦要持续工作，就需要 runtime

不是聊几句，而是要改代码、处理文件、维护状态、出错重试——像个真正的系统在运行。

2. 零碎的「记忆」「工具」「知识」需要工程化整合

memory、wiki、skill、profile、working memory 不是散落的 feature，而是一个系统的不同层次。

// 范式演进

Prompt、Context、Harness：三阶段到底差在哪

1️⃣ Prompt (2020–2022)

问题：「怎么说」

  • 核心是单轮指令
  • 人写 prompt，模型出结果
  • few-shot、CoT、self-consistency
instruction tuning prompt chaining

2️⃣ Context (2022–2024)

问题：「给什么背景」

  • 核心是多轮+检索
  • RAG、历史压缩、记忆管理
  • 但上下文还是「平面」的
RAG context window memory

3️⃣ Harness (2024–)

问题：「怎样搭 runtime」

  • 核心是结构化控制
  • 环境、工具、知识、反馈、约束
  • 人从写实现转向设计系统
runtime substrate state management feedback loops
从「说清楚」到「搭系统」

// Harness 五件套

Harness 的组成：环境、工具、知识、反馈、约束

环境层

Agent 工作的真实环境

文件系统、代码库、终端、浏览器

工具层

可调用的能力接口

函数调用、API、数据库操作

知识层

组织化的知识来源

文档库、代码库、知识库

反馈层

可观测的反馈回路

执行日志、结果验证、错误处理

约束层

安全与边界控制

权限控制、安全策略、资源限制

五层架构

// Runtime Substrate

runtime substrate：thread / turn / item / App Server

结构化会话模型

Thread会话主线：整个任务的上下文容器
Turn交互轮次：观察-思考-行动循环
Item执行单元：工具调用、文件操作等

App Server 能力

  • 状态压缩：历史不会无限增长
  • 持久化：会话可以中断、恢复、重播
  • 可观测：每一步都有日志、可调试
  • 并发控制：多 agent 协作时的状态同步
不是聊天，是结构化工作流

// 知识与状态挂载

Resource / Wiki、Profile / Memory、Skill、Working Memory 在 Harness 里的位置

📚 Resource / Wiki

→ 知识层：静态的、组织化的知识源

👤 Profile / Memory

→ 状态层：用户偏好、长期记忆，跨会话持久

🛠️ Skill

→ 工具层：可复用的能力模块

🧠 Working Memory

→ Runtime 层：当前会话的临时状态，会话结束可丢弃

层次清晰，各归其位

// 生产 vs 评测

生产 Harness 和评测 Harness 的关系

🎯 生产 Harness

  • 目标：把事情做成
  • 优化：成功率、效率、体验
  • 约束：真实环境的安全与限制

📊 评测 Harness

  • 目标：把过程测准
  • 优化：可复现、可比较、可归因
  • 输出：证据、轨迹、指标

✨ 两者共享核心逻辑

环境、证据、执行路径结构化

目标不同，底层相通

// 常见误解

最容易误解的 5 个点

❌ 误解 1：Harness = 高级 Prompt

✅ 纠正：Harness 是系统架构，Prompt 只是其中一个输入。

❌ 误解 2：记忆 = 长上下文

✅ 纠正：记忆分层，不是把所有东西塞进 context。

❌ 误解 3：Agent 越通用越好

✅ 纠正：工程化 Harness 是约束范围，而不是无限扩大。

❌ 误解 4：评测只看成功率

✅ 纠正：更重要的是可复现、可归因、可对比。

❌ 误解 5：必须用 OpenAI SDK

✅ 纠正：Harness 是设计思想，不是具体某个库。

澄清概念，少走弯路
