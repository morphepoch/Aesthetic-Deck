Harness Engineering
从 Prompt / Context 到 Agent Runtime 的工程转向

为什么我们需要从「写提示词」转向「设计智能体运行环境」

#Harness #Agent #Engineering

大家好，今天想跟大家聊一个我最近一直在思考的话题——为什么作为后端工程师，我们不能再只盯着 Prompt Engineering，而需要开始关注 Harness Engineering。

在过去一年里，我们见证了从 Prompt 到 Context 的演进，但现在，游戏规则又变了。今天我会用 15 分钟，把这个演进脉络讲清楚，然后重点落在——对我们写代码的人来说，Harness 到底意味着什么，要怎么落地。

好，我们开始。

01 · 为什么现在关心 Harness

因为单靠 Prompt
已经不够了

🔴 Prompt 时代

靠写好提示词，让模型给出准确答案。上下文短，知识固定，没有交互能力。

🟡 Context 时代

靠 RAG、长上下文、记忆系统，让模型回答得更准。但依然是一问一答。

🟢 Harness 时代

靠设计环境、工具、反馈回路，让智能体自主完成复杂任务。这才是未来。

第一个问题：为什么现在要关心 Harness？答案很简单——单靠 Prompt 已经不够了。

我们回顾一下：最早是 Prompt Engineering，靠写好提示词让模型干活。然后是 Context Engineering，靠 RAG、长上下文、记忆系统让模型回答得更准。但这些依然是「一问一答」的模式。

现在进入 Harness 时代。我们需要的不是让模型回答一个问题，而是让它自主完成一整个复杂任务——写代码、调工具、做决策、修 bug、甚至自己优化自己。

这时候，光靠写好提示词是远远不够的。我们需要设计一整套环境。

02 · 三阶段差异

Prompt → Context → Harness
核心范式在变

Prompt指令-响应 · 告诉 AI 每一步做什么2020–2022
Context上下文-理解 · 给 AI 足够的背景信息2022–2024
Harness目标-自主 · 告诉 AI 目标，让它自己想办法2024–

我们把这三个阶段放在一起比较，核心范式的变化就很清楚了。

Prompt 时代是「指令-响应」——我们告诉 AI 每一步做什么。Context 时代是「上下文-理解」——我们给 AI 足够的背景信息。而 Harness 时代是「目标-自主」——我们告诉 AI 目标，让它自己想办法。

这个转变本质上是从「人在回路里做决策」到「人在回路上做控制」——我们不再是司机，而是交通规则的制定者。

03 · Harness 的组成

五件套：环境、工具、知识、
反馈、约束

①
环境 Environment

让 Agent 在真实沙箱里工作（文件系统、终端、网络）

②
工具 Tools

API、函数调用、MCP、第三方集成

③
知识 Knowledge

RAG、文档库、知识库、静态资源

④
反馈 Feedback

检查结果、错误处理、人工介入

⑤
约束 Constraints

权限控制、边界、审批流程

好，那 Harness 到底长什么样？我把它拆解成五个核心组件。

首先是环境——Agent 需要在真实的沙箱里工作，有文件系统、终端、网络。然后是工具——API、函数调用、MCP 这些。接着是知识——RAG、文档库、知识库。

然后是两个特别重要但容易被忽略的：反馈和约束。反馈意味着 Agent 能知道自己做得对不对，能从错误中恢复。约束意味着我们能控制它不越界——权限控制、边界、审批流程。

这五件事合在一起，才是一个完整的 Harness。

04 · Runtime Substrate

Thread / Turn / Item
App Server 是核心

Thread
任务会话容器

隔离的上下文，可恢复、可追溯

Turn
推理-执行轮次

计划→执行→反思 的闭环

Item
原子工作单元

工具调用、状态更新、持久化

从工程实现的角度，Harness 下面的 Runtime Substrate 很关键。OpenAI 最近提到的 Thread、Turn、Item 这三个概念很有启发。

Thread是任务会话容器，提供隔离的上下文。Turn是推理-执行轮次。Item是原子工作单元。

05 · 各层位置

Resource / Wiki、Profile / Memory、
Skill、Working Memory
各归其位

这张图把大家经常混淆的几个概念理清楚了。

Working Memory是短期的，存当前任务状态；Skills是过程性的，存工具链；Profile/Memory是语义的，存用户偏好；Resource/Wiki是事实性的，存知识库。

06 · 生产 vs 评测

两套 Harness
一个核心

🏭 生产 Harness

真实环境与工具 · 实时状态管理 · 容错与降级 · 权限与安全

🧪 评测 Harness

沙箱化的任务集 · 结构化评估标准 · 自动化测试框架 · 证据链追溯

生产环境和评测环境各有一套Harness，但核心是相通的——都需要把环境、证据、执行路径和反馈回路结构化。

💾 持久化

🛡️ 隔离

Docker沙箱 · 权限边界 · 审计日志

# 最小架构 class HarnessEngine: async def run(self, task, ctx): while not task.done: action = self.planner.plan(task, ctx) result = self.executor.execute(action) task = self.checker.check(task, result)

对我们熟悉的工具来说，最小方案很直接——一个主循环，「计划→执行→检查」的闭环。
