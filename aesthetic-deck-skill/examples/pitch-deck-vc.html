02

WHY NOW

为什么后端工程师
开始关心 Harness？

Prompt 不够用了

只靠 \"system prompt + user input\"，Agent 无法在真实环境中完成复杂任务

Context 只是一部分

RAG、长上下文、记忆——这些都很重要，但它们只是更大架构中的一个组件

生产级 Agent 需要工程化

错误恢复、状态持久化、权限控制、可观测性——这些都是后端的老本行

核心转变：从 "我想让 AI 说什么" → 到 "我想让 AI 在什么环境下、用什么工具、遵循什么约束、完成什么目标"

为什么现在？因为我们发现——只靠 Prompt Engineering，根本做不出能在生产跑的 Agent。

我举个例子：假设你想做一个\"帮工程师修复线上Bug\"的Agent。你光给一个Prompt说\"你是资深工程师\"有用吗？没用。因为Agent需要：读Log、查文档、看代码、本地复现、写修复、跑测试、发PR——这些根本不是Prompt能搞定的。

Context Engineering往前走了一步，但还是不够。

03

EVOLUTION

Prompt / Context / Harness
三阶段差异

Phase 1 · Prompt

指令 → 响应

告诉 AI "每一步做什么"，期望确定性输出

Zero-shot Few-shot CoT

Phase 2 · Context

上下文 → 理解

给 AI "足够背景"，期望它基于信息推理

RAG 长上下文 记忆

Phase 3 · Harness

目标 → 自主

告诉 AI "目标是什么"，让它在约束内自己想办法

环境 工具 反馈 约束

核心公式

Harness = 环境 + 工具 + 知识 + 反馈 + 约束

这三阶段不是互相替代的，是层层叠加的——Harness包含了Context，Context包含了Prompt。

我再用刚才\"修Bug\"的例子对比一下：

Prompt阶段：你写\"你是资深SRE，帮我看看这个错误日志\" → AI看完说\"这看起来像是个数据库连接问题\" → 没了。

Context阶段：你不光给错误日志，还把相关的Wiki文档、最近的代码变更都通过RAG塞进去 → AI能给出更准确的分析，但还是没法执行操作。

Harness阶段：你说\"目标是把这个Bug修复并部署\"，然后给它一套环境和工具 → AI自己就能把事办了。

04

ANATOMY

Harness 的 5 大组成

环境 Environment

Agent 运行的"地方"：容器、沙箱、文件系统、网络访问、云资源

例：一个完整的开发环境，能跑测试、能执行 Git 命令

工具 Tools

Agent 能"用"的能力：函数调用、API、CLI、SDK

例：search_code()、run_tests()、create_pr()

知识 Knowledge

Agent 知道的"东西"：文档、Wiki、代码库、历史对话、用户 Profile

例：团队的编码规范、过往的Bug修复记录

反馈 Feedback

Agent 收到的"信号"：工具执行结果、用户确认、测试是否通过、环境状态变化

例："测试挂了，错误是XXX"、"这个PR已被批准"

约束 Constraints

Agent 不能"碰"的红线：安全策略、权限边界、成本限制、时间预算

例：不能删生产数据、API调用不能超过 $10/天

关键洞察

这五件事，没有一件是模型本身做的——它们都是 我们作为工程师要搭出来的 "基础设施"

这一页是核心——Harness的5大组件。

再强调一遍：这5个组件没有一个是模型本身负责的——模型只负责"思考"和"决策"，但在哪思考、用什么工具思考、基于什么知识思考、思考完的结果怎么反馈、思考过程有什么约束——全是我们要写代码实现的。

你现在应该明白为什么后端工程师开始关心这个了——这不就是我们天天在干的事吗？

05

ARCHITECTURE

Runtime Substrate & 知识层/状态层

Runtime Substrate

Thread 会话级别上下文
Turn 单轮交互
Item 单个执行项（工具调用、推理等）
App Server 承载整个系统的服务

知识层 & 状态层

Resource / Wiki 静态知识（检索增强用）
Profile / Memory 用户/Agent 长期记忆
Skill 可复用的能力模块
Working Memory 当前任务的短期工作区

架构关系

Resource/Wiki 是检索源 → Skill 是可执行模块 → Profile/Memory 是持久状态 → Working Memory 是当前上下文窗口，这些都在 Harness 框架内协同工作

这一页回答很多后端工程师最关心的问题：这些东西在架构上怎么放？

Runtime Substrate：Thread对应整个会话，Turn对应单轮交互，Item对应单个执行项（比如一次工具调用），App Server承载所有。

知识层和状态层：Resource/Wiki是静态知识（供RAG检索），Profile/Memory是长期记忆，Skill是封装好的能力模块，Working Memory是当前任务的短期工作区。

06

PERSPECTIVE

生产 Harness vs 评测 Harness

生产 Harness

面向真实用户、真实环境、真实任务

  • 高可用、容错、错误恢复
  • 安全控制、权限边界
  • 可观测性（日志/指标/追踪）
  • 成本优化和限流

评测 Harness

面向 Benchmark、可复现、可比较

  • 环境标准化、隔离
  • 证据留存、执行路径记录
  • 评分系统、Metric 收集
  • 支持 A/B 测试和对比

相同点

两者共享核心概念：都需要把 环境、工具、知识、反馈回路 结构化出来

很多人会忽略：生产环境的Harness和做评测的Harness关注点不一样。

生产环境关心：高可用、容错、安全、成本、可观测性——这些是后端工程师的老本行。

评测环境关心：标准化、可复现、证据留存、评分系统——为了公平比较不同方案。

但两者的核心骨架是一样的：都需要把环境、工具、知识、反馈回路这些东西结构化地管理起来。

CLARIFICATION

最容易误解的 5 个点

❌ Harness 不是 Prompt 的新名字

Harness 包含 Prompt，但远不止 Prompt——还包括环境、工具、反馈、约束等

❌ 模型不是越强大越好

在 Harness 框架下，合适的工具和约束往往比一味堆模型能力更重要

❌ Harness 不只是 AI 团队的事

后端、安全、DevOps 都能发挥巨大价值——这是系统工程问题

❌ 不要一开始就追求完美

先跑通最小闭环，再逐步迭代——这和我们做其他系统是一样的

❌ 不要忽略安全

Agent 能调用工具，意味着风险也被放大了——沙箱、权限控制、审计日志一个都不能少

最后澄清几个最常见的误解。

第一，Harness不是Prompt的新名字——Harness包含Prompt，但远不止Prompt，还包括环境、工具、反馈、约束等。

第二，模型不是越强大越好——在Harness框架下，合适的工具和约束往往比一味堆模型能力更重要，也更可控。

第三，Harness不只是AI团队的事——后端、安全、DevOps都能发挥巨大价值，这本质上是系统工程问题。

第四，不要一开始就追求完美——先跑通最小闭环，再逐步迭代，这和我们做其他系统是一样的。

第五，不要忽略安全——Agent能调用工具，意味着风险也被放大了，沙箱、权限控制、审计日志一个都不能少。
